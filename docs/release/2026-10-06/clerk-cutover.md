## Migration contract and historical qualification

The migration copies independently verified identities into the explicit production instance and reassigns their existing app accounts. It does not copy passwords or sessions, merge accounts by email, or replace internal app UUIDs. Existing libraries, progress, preferences, interactions, moderation and future owner foreign keys are verified using full row hashes.

The pre-cutover private source inventory contained all six profiles visible in the source instance: four real verified identities and two excluded synthetic test addresses. Its read-only plan covered all four real app accounts, with 346 direct owned/relationship rows represented in private snapshots. Inventory completeness was independently checked against the six source profiles inspected in Chrome. At that qualification stage, no production identities had been created or reassociated; the later actual cutover above supersedes that pending state.

Migration state and source/production credentials remain private, owner-only files. The actual cutover receipt verifies state mode 0600. No real Clerk writes or production reassociation were performed by the earlier synthetic qualification; actual identities/apply execution is separately recorded above. Do not expose state contents or credentials in this handoff.

Run the compiled CLI with Node24 from the qualified artifact (`node dist/scripts/migrate-clerk-production.js`); the source checkout also supports `node --import tsx src/scripts/migrate-clerk-production.ts` for local operator work. Every invocation uses explicit paired arguments:

```text
--mode plan|identities|refresh|apply
--inventory /absolute/private/source-users.json
--source-config /absolute/private/source.env
--state /absolute/private/migration-state.json
--expected-source-count 6
```

Production modes additionally require `--production-config /absolute/private/production.env` and `--instance ins_…`. Credentials are read from private files and never logged or passed as argument values. The destination secret must be a production key, and the API instance ID/environment must match. Inputs and state must be real private files. A per-state exclusive lock prevents concurrent overwrites; after an abrupt process kill, verify the recorded PID is no longer alive before removing a stale private `.lock` file.

Sequence:

1. Independently verify the complete source inventory. Run `plan`; source reads occur in a repeatable-read, read-only transaction. A plan can be regenerated while it has no production association.
2. Apply the account-deletion migration and initialize the trusted independent deletion ledger. Configure `CLERK_EXPECTED_ISSUER` as the exact origin of the actual production Frontend API. Remove the source test-instance `CLERK_JWT_KEY`, or replace it with the matching destination public key; adding a live secret alone does not supersede a configured local verification key. Verify a production session token is accepted and a source test-instance token is rejected. Stop the source app service. Production modes verify that its configured loopback port is closed, reject both DB tombstones and independent precommit deletion intents, and require an existing trusted ledger.
3. Run `identities`. Only explicit `previously-development:<sourceID>` mappings are reused; otherwise a destination user is created. Verified primary email ownership and active ban state are checked again. Instance association is saved before the first create, so a lost response can resume through the explicit external ID without a duplicate user. A foreign destination app account is rejected before banning/reassigning it.
4. If owned data changed since the plan, run `refresh` while stopped. This performs only Clerk reads and DB reads, retains every production mapping, and updates the full data snapshots. It refuses ownership/moderation changes that need explicit resolution. Never overwrite a live mapping with `plan`.
5. Run `apply`. Every destination identity is revalidated. One DB transaction locks identity mappings, checks ownership/deletion/full hashes, changes only `users.clerk_id` and the matching moderation identity, and verifies unchanged UUIDs/full owned data. A lost commit acknowledgement resumes safely against the already reassociated UUIDs.
6. Save the private state, take a new post-cutover backup, and restore that exact dump into a removed scratch database before using it as the consumer recovery baseline. An earlier dump contains development Clerk identifiers and needs a separately qualified identifier translation before the production deletion ledger can sweep it correctly. See [identity-cutover recovery](identity-cutover-recovery.md). Verify production sign-in, known-user libraries and account deletion on the qualified candidate. Synthetic addresses remain excluded. Existing sessions must sign in again; no session/password transfer is promised.
