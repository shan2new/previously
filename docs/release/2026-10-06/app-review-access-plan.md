## Evidence and practical limits

- Clerk's current official OpenAPI specifies `bypass_client_trust` on both `POST /v1/users` and `PATCH /v1/users/{user_id}`, and returns it on the user object with a default of false. The documented effect is skipping Device Trust checks for that user during sign-in. This is narrower than disabling the instance rule. [Clerk API schema](https://github.com/clerk/openapi-specs/blob/main/bapi/2026-05-12.yml), [official Python SDK reference](https://github.com/clerk/clerk-sdk-python/blob/main/docs/sdks/users/README.md).
- Direct requests can select `Clerk-API-Version: 2026-05-12`. Previously's installed `@clerk/backend` is 1.34.0, whose user parameter types lack this field. Use the official REST endpoint for this provisioning operation; no dependency or frozen runtime change is needed. [Clerk API versioning](https://clerk.com/docs/guides/development/upgrading/versioning).
- The installed native package resolves to ClerkKitUI 1.5.8. Previously uses its public `AuthView(onAuthComplete:)` from `ios/Sources/Auth/SignInView.swift`; the SDK supports password and alternative-method screens. Separate actual native receipts above prove the two direct-password logins.
- [Production readback already requires passwords and prefers the password strategy](/Users/shan2new/Projects/previously/docs/qa/2026-10-06/app-store/review-otp-investigation.json). The reviewer has a password, a client-trust exception and no MFA. No preference or security change was needed. The approved notes retain an alternative-method fallback for a previously opened screen; fresh reviewer login went directly to Enter password.
- Production test mode is explicitly discouraged by Clerk. A reusable `424242` test email would require enabling that global mode and does not provide the same account isolation. [Clerk test identities](https://clerk.com/docs/guides/development/testing/test-emails-and-phones).
- A username-only account would require changing currently disabled username settings. Clerk's user model needs an enabled authentication identifier, and Device Trust documents a verified email/phone limitation; those facts alone do not prove a reliable username-only review login. There is no need to add this new consumer strategy. [Clerk user creation](https://clerk.com/docs/reference/backend/user/create-user), [Device Trust](https://clerk.com/docs/guides/secure/device-trust).
- The per-user flag has no paid-plan requirement stated in its schema. Its actual provisioning/readback and native use passed on the existing free production instance; no plan change or global rule change occurred.
