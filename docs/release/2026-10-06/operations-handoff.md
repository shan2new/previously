## Final intended retention

The release owner selected seven daily app-database backups and 30 days of aggregate usage/metrics snapshots. Sanitized logs use capped daily files, pruned seven days since each file's last entry; with timely pruning, the oldest record can approach eight days. This is a file-age rule, not exact seven-day per-record expiry. No weekly archive, indefinite raw request log or paid analytics service is intended. Support correspondence is retained as needed to resolve requests and required records; no arbitrary deadline or automated deletion from the operator’s personal inbox is promised.

The schema also contains `moderation_bans`, keyed by raw Clerk identifier with a reason and created/lifted timestamps. It deliberately survives account deletion and currently has no expiry. This separate security retention is disclosed in the published effective policy; a stronger statement that only a hash remains requires an actual schema/data change and verification. Public comments off does not erase older moderation records.

Backup storage belongs in a private owned directory outside the web root, with directory mode0700 and dump/manifest mode0600. Keep credentials in private config and subprocess environment, never command-line arguments or evidence files. Record UTC timestamp, source fingerprint, database/schema version, dump byte size, SHA256 and parsed restore TOC. Atomic rename only after dump and verification succeed; a failed run must not replace the most recent valid backup. Prune only files positively owned by this backup job and only after a successful verified dump. Read-only dump creation is safe; restore must target a newly named isolated database first.

Count retention and age retention differ. Seven retained daily backups alone can retain data for much longer than seven days if the job stops. Enforce backup age pruning and monitor job freshness. The public policy’s backup age must match actual pruning; log policy must describe the seven-day last-entry file-age rule and approximate eight-day record bound. Apply explicit age pruning to 30-day snapshots too. A stopped collector cannot establish any live expiry guarantee.

## A restored database must preserve deletion

An old database dump can recreate a deleted user and forget a newer account-deletion tombstone. Preserve an authoritative current deletion ledger independently of ordinary rolling backups. Before any restored database is reachable:

1. Keep the app listener/tunnel target stopped or in maintenance; verify it cannot serve authenticated traffic.
2. Restore the verified dump to a new database name and apply compatible migrations.
3. Merge the current pending/completed deletion ledger, retaining completion and never downgrading a completed deletion.
4. Remove account-owned app rows for every retained deletion marker. Completed markers hold only identity hashes; a database join must hash `users.clerk_id` to match them. Pending records also include the raw ID required for provider retry.
5. Verify no deleted identity can upsert an account or read account data. Resume pending provider cleanup without pretending it has completed.
6. Test representative non-deleted libraries/progress and owner isolation, then switch the service to the restored database and perform public-path checks.

If the authoritative current ledger is missing, do not reopen an older restored app database. Use the known current store/ledger or obtain a recovery decision from the owner. A same-disk ledger/backup supports accidental change/process recovery; it does not protect against total Mac/storage loss. An off-device copy requires a verified existing storage destination and truthful cost/access assumptions, not an invented free cloud guarantee.

Clerk cutover adds an identity-realm boundary: take and qualify a new post-cutover backup before selecting the consumer recovery baseline. An earlier dump holds development identifiers, while later erasure markers hash production identifiers. The ordinary restore tool does not translate these. Follow [identity-cutover recovery](identity-cutover-recovery.md); do not reopen a pre-cutover dump or reinstall the mutable development plist as an assumed production rollback.
