## Safe operator boundaries

- Default `status` and local `prepare` make no network requests or credentials. `preflight` performs GET requests only; it checks the actual production instance, production test mode off, existing email/password settings, owner-alias restrictions, and the exact five protected identities.
- Future `provision --owner-action-authorized` is the only provider mutation path: one isolated `POST /users`. Root obtains any required final action-time owner approval before invoking it. It creates a unique private password only then, saves credentials and the create-attempt journal before sending, and resumes by the exact external ID. A timeout, rejected/unknown response or missing formerly known user never triggers a second create.
- An unrelated existing external ID or normalized-email collision stops execution. The operator neither adopts that user nor modifies any existing identity. It cannot PATCH, DELETE, create sessions, seed app data or change instance settings.
- `mark-deletion-start --owner-action-authorized` writes a local irreversible run marker before the approved consumer action. It does not send deletion. Once this marker or provider absence is recorded, provisioning is permanently refused for this identity. Do not recreate it afterward to obtain a cleaner receipt.
- `verify-provider` performs GET requests only. It requires the exact recorded disposable identity and checks the five protected identities/security projections are unchanged. A defined Clerk `404 resource_not_found` means provider absence; authentication failures, unknown 404s and network failures do not. Provider absence alone leaves app/restart proof pending.

No live authorization flag is needed for the synthetic guard tests. Their inputs are in-memory fakes and they perform no provider requests or real credential creation.
