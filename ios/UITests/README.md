# Native QA harness

The `PreviouslyQA` scheme builds the `QA` configuration and runs `PreviouslyUITests` serially. The app has its own bundle (`com.cognipin.previously.qa`), its widget has a matching QA bundle, and QA source hooks compile only with `PREVIOUSLY_QA`. The normal Debug and Release identifiers are unchanged. The test runner explicitly opens the QA app, refuses non-loopback API URLs, and requires the scratch server's control token before any mutation.

Start the scratch fixture server documented in `ios/Tools/qa/fixture-contract.md`. Regenerate the project from `ios/project.yml`, then use XcodeBuildMCP's test workflow with project `ios/Previously.xcodeproj`, scheme `PreviouslyQA`, configuration `QA`, one simulator, and the runner environment below. The XcodeBuildMCP CLI supports a `testRunnerEnv` object; keep the actual control token in the invocation/environment, never in a shared scheme or checked-in file. There is no paid service or device farm.

| Runner variable | Default / use |
| --- | --- |
| `PREVIOUSLY_QA_CONTROL_TOKEN` | Required; scratch control token, excluded from evidence |
| `PREVIOUSLY_QA_BASE_URL` | `http://127.0.0.1:18787`; explicit `127.0.0.1` HTTP only |
| `PREVIOUSLY_QA_SEED` | `20261006`; decimal UInt64 |
| `PREVIOUSLY_QA_DURATION_SECONDS` | `60`; bounded to 10–300 seconds |
| `PREVIOUSLY_QA_MAX_ACTIONS` | `80`; bounded to 5–1,000 decisions |

For an initial smoke run, select `PreviouslyMonkeyTests/testSeededMonkey` and use 10 seconds / 10 actions. After relevant changes, use fixed seeds `20261006`, `60102620`, `38654705664` at 300 seconds each. These budgets are starting points, not a certification. Each run reports completed actions, unavailable selections, assertions and visited states separately. The deterministic five-root warm-up and final relaunch happen outside the random duration budget.

`QAHarnessTests` verifies the deterministic generator and refuses unsafe hosts. These fast tests test the harness, not the app. `PreviouslyDirectedTests` includes progress and Undo across entry points/relaunch, three rapid episode-ring marks through background/foreground, a response dropped after a canonical commit, account A → B library isolation through relaunch, and a delayed search followed by a replacement query. Three focused regressions cover an older failed progress intent after a newer accepted value, a failure row updated twice before Retry, and an old Retry during a delayed newer write; each rejects all three API attempts before commit and checks the independent canonical value. Run these when their areas change. The dropped-response test checks canonical progress effect count; it does not establish conflict ordering across multiple devices.

`AccountLocalStoreTests` compiles the production storage and export staging helpers into the test bundle and checks stale-owner writes, teardown removal, unowned-file migration, cold signed-out cleanup, account-specific restoration, rejected stale exports, and preservation of a user-saved copy in disposable directories. `AccountDeletionRequestTests` compiles the actual production one-attempt request decoder and checks the fresh Apple proof body, absent-proof deletion, defined pending/complete metadata and unknown receipt holds. `ImportModelTests` compiles the real import-progress contract and checks old saved progress without omissions, separate adult-policy counts, Codable restoration, and preservation through interrupted-job conversion. `PreviouslyDeletionTests` defines committed deletion with a lost response through relaunch/reconciliation, complete and pending cleanup notices, a definitive refusal that resumes tracking and saved manual Apple-disconnection instructions across cold launch. These tests mutate only synthetic accounts. A passed client test against the fixture does not verify real Clerk cleanup or the production deletion worker.

`PreviouslyAccountIsolationTests` keeps an accepted account A progress request in flight while the actual UI signs out and signs into B, then checks canonical B state and every authenticated progress request. A separate failed-write case checks that A's Retry row and local library do not return in B's session or after relaunch. An already-sent A request may commit on the server after cancellation; the invariant is that it never uses B's token or local storage.

Progress regressions also inspect the three mutation headers. Retries and cold-launch replay must retain the same operation/writer/sequence; a changed intent requires a different operation and a higher sequence from the same writer. The synthetic fixture validates and logs that metadata; durable server ordering is qualified separately against real HTTP/PostgreSQL.

The storage regression also uses the production mutation clock to verify the same writer and an increasing sequence survive relaunch and ordinary logout/relogin while content caches are purged. A stale or missing owner cannot mint a stamp, and B receives a separate writer identity. Only the minimal random writer/counter survives ordinary logout; accepted deletion clears that clock too.

Every native case terminates the QA app, resets synthetic backend state, and clears only the QA bundle's local state on its initial launch. Relaunch checks omit that reset. Synthetic account `fixture-a` owns `qa-anime` (media 1001, 3/12 episodes) and `qa-tv` (media 2001, 2/8); `fixture-b` owns only `qa-plan` (media 3001, 0/10). Progress is compared with the independent `/__qa/state` HTTP oracle rather than derived exclusively from the same app model being tested. Fault controls require `X-Previously-QA-Token` and are restricted to the scratch server.

The monkey chooses 40% navigation, 30% next episode / Undo, 20% search and 10% profile open/dismiss. It only activates known app controls that exist and are hittable in the current state. An unavailable category is recorded rather than counted as successful coverage. Scrolls target named root/detail scroll views; no random screen coordinates are used. Action IDs select actual Buttons, avoiding SwiftUI identifiers inherited by caption text. Discover's opener is activated before text entry; because its real Button carries a search-field accessibility trait, only the exact opener ID permits a SearchField tap fallback. The system-owned `.searchable` text field uses the sole visible SearchField excluding that opener when it has no custom ID; the episode tab has an English `Episodes` system-label fallback. These fallbacks are recorded under stable logical targets in the trace.

Input is typed in 16-character chunks with an exact prefix assertion after each chunk. Traces record both requested and observed input; truncation remains a failure. QA seeds fixture-a only once per reset sandbox, preserves a remembered fixture-b, and preserves actual sign-out across relaunches.

Ordinary next-episode marks use the real detail post action, which produces an Undo receipt. The episode-ring case uses the real next-ring control; regular ring marks intentionally do not produce the same receipt. No alternative test-only progress-writing button is added. QA read-only accessibility markers expose ready/identity/current progress so invariants can be asserted without changing write behavior.

Each case attaches a JSON action trace (seed, ordered action/target/outcome, fault schedule, duration, assertions, states and OS), a final screenshot and the accessibility hierarchy to its XCTest result. Preserve the result bundle with the source revision and simulator/device record. A seed fixes action selection; the trace and fault schedule are still necessary to reproduce asynchronous behavior. Reduce any failure to a directed regression before broad random runs resume.

Not covered by this fixture: imports through the actual Files picker, offline queue recovery across a long process interruption, production Clerk deletion/cleanup workers, full VoiceOver and largest-text behavior, a physical TestFlight candidate, and arbitrary third-party authentication/OS dialogs. New test cases need recorded native execution before being counted as verified coverage. Keep those explicit in the QA report; a short clean simulator run cannot prove them. The release planning matrix remains in [monkey-qa.md](../../docs/release/2026-10-05/monkey-qa.md).

## Pre-dispatch durability qualification

`MutationJournalTests` compiles the actual production helper and reconstructs it from real atomic files. Six cases cover cold restoration, original/followup stamp preservation, newer-intent receipt safety, stale owners, file-write failure, and corrupt/unreadable restoration. `PreviouslyDurabilityTests` holds real app requests before commit or after commit before receipt, terminates the process before any catch, then taps the restored Retry and compares the original stamp, UI and independent canonical state. The account-isolation case also requires a new monitor generation and a real NWPathMonitor callback after logout/login. Focused durability and monitor cases have passed; the current final candidate requires a fresh 42-case core receipt and all three 300-second seeded runs.

The optional `PreviouslyTrailerTests` uses an explicitly enabled known YouTube video and the actual provider bridge to inspect privacy mode, transient website storage and playback/control continuity. It is separate from the dependency-free core fixture/monkey selection. Its inline fullscreen tap uses the screenshot-observed physical control and recorded card bounds, with actual provider state and clock confirmation; it is not a full VoiceOver qualification. Default synthetic catalogue payloads contain no remote media; no external trailer request occurs until that separate case opts in.
